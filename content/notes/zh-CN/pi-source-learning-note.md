## 这场面试

上周周末，我参加了一场 CEO 面试。岗位是 Agent harness 研发，公司是做自研 Agent 框架的。

面试前做了一些题目，其中一个是：不用框架，去实现一个最小的、可用的 agent。面试的时候会拷问代码，要求能理解 AI 写出来的代码。

整体下来，我表现得不好。对代码的拷问没怎么接住。agent 方面的知识一旦落到代码上，我就理解得不够。

有一道题现在想来其实很简单：「为什么工具的结果要写回 session？」我当时是从 message 的角度答的，大概意思是：LLM 看不到返回结果，那就没有对应输出。面试官认为这不是重点，也不是原因。他给了时间让我找代码，我最后还是没答上来。

他点了我一下：loop 既然是个循环，第一轮执行完后，它要不要判断第二轮怎么办？下一轮要上一轮的输出。

后来我去看了 agent 源码，主要是 Pi，也对照过 nanocode。中间我还误以为：如果没有结果返回，后面每一轮就启动不了，会一直陷在死循环里做同一个决策。这个理解不对。循环还是会转的。每一轮发给模型的请求，就是用当前这堆对话消息组装出来的。工具跑完后，如果不把结果写回这些消息里，模型下一轮仍可能看到「我调用了这个工具」，但看不到结果，于是可能再调一次，或者没法走出下一步。

后面还问了一些问题，我也没回答上，但那些答案其实都可以从代码里找到。面试官建议，学 agent 要去看源码。我的基础还不够，得多看源码。简历里写了 Pi，他问我有没有看过 Pi 的代码，当时还没有，他很震惊。

不过面试官人很好。虽然我表现得很差，他还是耐心给我时间看代码、思考，并给了建议。

## 如何学习 agent——看源码

听完这个建议，我开始对照下面这张图读 [Pi](https://github.com/badlogic/pi-mono) 的源码。我还没有全部看完，下面顺着这张图的结构，写下目前能说清的流程和设计。

导图比较宽，[点击可看大图](/asset/pi-runloop-mindmap.png)。原图在 [Excalidraw](https://excalidraw.com/#json=oY6yvZdKMAenaOtxkVWSf,0iGG_OgKqNg1nrNPwHdd4Q)。

[![以主循环为中心的思维导图](/asset/pi-runloop-mindmap.jpg)](/asset/pi-runloop-mindmap.png)

整张图先从最上面的 runloop 分成两支：左边是外循环，右边是内循环。图更左边、框在 runloop 外面的，是 Agent 的入口和插话；图右边伸出去的，是问模型和执行工具。一个可用的 agent 不是一问一答就结束，而是这两层循环转起来的。

先看框外左边。上面是一个插话队列，负责入队、取出和清空。插话分两种时机：循环正在做的时候插进来，叫 steering，像做饭时放盐；本轮正要结束时再补一句，叫 follow-up，像做完饭再加个汤。再往下是 Agent 的两条入口。平时新开一轮走 prompt，而且要等上一轮循环真正做完，才会再开下一句。另一条是 continue：循环中途异常停了，但后面还有话要继续时，把同一段上下文再续上——前提是现在没有正在跑的循环，并且上下文末尾已经是工具结果或用户的话。这两条路最后都要经过同一道门：同时只能有一次在跑。因为跑的时候会改同一份对话记录，平行开跑会互相踩。执行、出错、结束都要收尾，下一次才能再开。用户点停止、请求失败，常见也是走这条收尾。

再看外循环。内循环做完以后，它先问：还有没有 follow-up？有的话，把话放到插话队列里，再进内循环。外循环里还有一块通知：循环把已经发生的状态变化发出来，用来更新自己的状态，并叫醒外面事先订好的监听，比如刷新界面。没有这套通知，循环也能转，但会话和界面需要它。监听是在用户开口之前就订好的；订了的人不会去执行工具。

内循环按图上从上到下走。它先问这一圈要不要转：还有没有工具要跑，或者有没有插话要处理。一开始会先假定「还有后续」，为的是即使这轮对话里没有工具调用，循环也能走下去。从第二轮起，下一圈还没开始时，先做一步准备：要不要压缩上下文、换模型或改思考强度，用来覆盖下一轮；没有变化就原样。这段时间也会检查插话，有就排进队列——还要看队列是不是空的，免得打断「一次只处理一条」。然后这一轮才正式开始。接着把当前对话装配成这一轮的上下文，最后再确认一次模型配置，再拿去问模型。模型回来后，得到的可能是工具结果、一句回复，或者空的，都并进总的消息列表。

问模型和执行工具，在图的右边，是内循环中段伸出去的两块。流式输出之前，先把过长的上下文裁一裁，再把给界面看的消息转成模型认识的消息。这两套不是同一套：界面可以插一条「正在读取文件…」给用户看；发给模型时，认不出的自定义信息会被过滤掉。流式那边的循环主要在记账，并不执行工具：记下回复开始了、工具调用开始了、结束了，再把这些变化通知出去。真正执行工具是另一块。它先看消息里有没有工具调用；如果回复因为长度被截断，这一轮的工具调用会全部判失败、写回消息，并让内循环再走一轮，而不是拿着半截参数去跑。没有这类问题，才真正执行，可以串行或并行。结果仍要按调用顺序写回。写回的原因前面已经说过：不是「不写回循环就会停」，而是下一轮的输入就是当前这堆消息。

内循环走到最后，交给 finishTurn：让外面判断执行完后做什么，一般是结束，或再继续。图上这里分成三条出口。一条是错误或中止，这种强制退出，finishTurn 管不住。一条是判断工具调用有没有因为超出长度被截断、不能执行；如果上面其实是空回复，就要明确关掉「还有后续」，否则内循环会空转。一条是正常执行完的退出。正常退出之后，还有一种情况：有时外面改了模型配置，需要拿旧上下文再让模型表个态，会再跑一次，跑完就把这个标记关掉。

像 nanocode 这类更小的实现，循环里没有「下一轮开始前先准备一下」这一步，上下文只会一直变长，要清就整段清掉。这是对照之后才看得更清楚的设计。

我确实还没有把源码全部看完，图上更细的地方以后再补。不过还是想建议大家去读一些 agent 源码，常常会有别样的感悟。
