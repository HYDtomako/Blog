读 Anthropic 那篇[「用一队并行 Claude 造 C 编译器」](https://www.anthropic.com/engineering/building-compiler)，真正值得记下来的不是那个编译器，而是作者怎么把「对错」这件事拆成三层。

我把这三层串成一条链：

verifier 定「什么算对」→ harness 定「agent 怎么知道对没对」→ oracle 定「并行时怎么各自知道对不对」。

下面逐条拆。

## 一、verifier 定「什么算对」

自主 agent 最反直觉的一点：没有人在场纠偏，唯一能约束它的就是测试。于是「agent 会做成什么样」，被「你的测试允许它做成什么样」彻底决定——verifier 不严，它不会失败，只会安静地把问题解成它理解的样子，而测试还是绿的。

这把 verifier 从「验收环节」提到了「能力天花板」的位置。作者的做法不是写完测试就收工，而是把它当活物养：找高质量的现成测试集、给真实开源项目写 verifier、盯着 Claude 犯什么错再针对这个失败模式补测试；项目后期它频繁「加新功能就弄坏旧功能」，就补 CI、加回归门禁。一句话，测试是从 agent 的实际翻车里长出来的。

这是整条链的地基——后面两环都在复用同一个「对」的定义。

## 二、harness 定「agent 怎么知道对没对」

有了 verifier，还得让 agent 在无人值守时能读到它的结论。这一环的关键不是写工具，是换视角：作者反复提醒自己「我是在给 Claude 写测试工具，不是给我自己写」。

换视角具体落成三条，命中都是 agent 相对人的先天缺陷：

1. 上下文是稀缺资源 —— 测试少打日志。人看几千行没关系，agent 的窗口会被占满。所以最多打几行，细节写进文件让它按需去翻；错误写成 `ERROR …` 同一行方便 grep；汇总统计预先算好，别让它每次重算。
2. 没有时间感 —— 时间盲要兜。它分不清「刚跑 5 秒」和「已经跑了 3 小时」，丢那儿能跑几小时测试而不推进。所以进度低频打印（低频是为了省上下文，不是输出慢），并给一个默认的 `--fast` 只抽样 1% / 10%，让每轮几秒就出结果。
3. 无状态冷启动 —— 用文件当记忆。每个 agent 都是新容器、零上下文，所以 harness 里写死要求：维护详尽的 README 和进度文件。等于让文件承担 agent 之间的「交接班记录」。

所以 harness 回答的是「agent 怎么知道对没对」：把 verifier 的结论，翻译成 agent 在自己那些限制内能消费的形式。人不会被日志淹死、会感知时间、有记忆；agent 三样都没有，harness 就得替它兜住。

## 三、oracle 定「并行时怎么各自知道对不对」

前两环解决的是单个 agent。一并行，问题换了形态：任务若能被切成彼此独立的单元，并行是白送的（每个 agent 修一个独立的失败用例）；但如果它是个不可拆的整体——比如编译整个内核——16 个 agent 会全撞在同一个未解决的失败上，修同一处、互相覆盖，人再多，有效工作还是 1 份。

这里的钥匙是一个已知正确的参照物，也就是 oracle。GCC 就充当这个角色：故意把大部分文件交给 GCC 编、只让 Claude 编一小部分，于是全局的、二值的「内核起不来」被局部化成「这几个文件里出了问题」，再二分缩小范围。失败信号一旦能定位到文件，就重新长出了可以各自认领的子任务，并行才真正成立。

所以 oracle 回答的是「并行时各个 agent 怎么各自知道对不对」：它把一个大目标切成许多个「自己也能跟标准答案比对」的小目标——这正是并行缺的那块地基。

收束

这三段不是三个并列的技巧，是同一条原则的三次落地：自主 agent 的上限，不由模型决定，而由你给它造的环境决定——判断对错、感知进度、消解冲突。

- verifier 定「对错」的定义；
- harness 把这个定义翻译成 agent 能读的信号；
- oracle 把信号复制给每一个并行的 agent。

对照另一篇里那句「grader 决定 eval 的上限」，这里是同一句话搬进了生产：verifier 决定 agent 能走多远。

再往外推一层，这也解释了 agent 产品的差异化会往哪儿走：当大家都会搭 agent，「功能」这一层就不再有护城河了——能拿出来的差异化，只剩「我的 agent 真做成了什么」。而「真做成什么」，恰好就是这条链在决定的东西：你怎么定义对错、怎么让它知道对没对、怎么让一队 agent 各自都算数。
